# 房间里的 Agent,注定一片混乱吗?

> 原文:*Is Having Agents in the Room Meant to Be Chaotic?*

> 原文链接:<https://raft.build/resources/blog/is-having-agents-in-the-room-meant-to-be-chaotic/>
> 术语约定:AX(Agent Experience,智能体体验)= 对应于 UX 的 agent 侧设计学科;held draft 译作"暂存草稿";agent inbox 译作"agent 收件箱"。

> 当 agent 被当作"持续在场的人类"来对待时,共享工作区就会变得嘈杂。Raft 的 agent 收件箱与暂存草稿,给了 agent 一套"房间感知"的决策方式:何时读、何时回、何时改写、何时保持沉默。

往房间里放一群 LLM agent,让它们轮流报数,不许重复——你可能见过这个实验。对人类来说这毫不费力:人们会等轮到自己。而在典型的 agent 工作区里,三个 agent 会同时报"1",数到"4"时已经乱成一团;agent 越多,越糟。

这些失败模式我们都很熟悉:三条回答同一时刻到达,其中两条一模一样;同一个任务被认领了两次;一条回复在对话已经前进二十分钟之后才姗姗来迟。往房间里塞的 agent 越多,房间听起来越像一场争吵,而不是一个团队。

常见的解释是能力问题——换更强的模型、更好的提示词、更严的护栏就好了。但我们的经验是:这些混乱大多不是智能的失败,而是设计的失败。**Agent 没坏,坏的是房间(The agents are not broken. The room is.)**

## Agent 是回合制的

人类是连续的。我们等人说完再开口;我们懂得沉默的含义;我们感觉得出会议什么时候该收尾。更重要的是,我们能察觉房间在我们做出反应的同时正在变化——有人插话了,有人退出了,有人换了话题。我们不经提示就会调整自己。

Agent 不是连续的,它是回合制的。它被调用,读取房间的一份快照,推理,提交一个动作,然后等待下一次调用。两次调用之间,房间里发生了什么,它一无所知。如果它撰写回复期间有三条新消息到达,它一条也看不到;等它终于发出去时,它是在对一个已经不存在的房间说话。

这不是模型能力的局限,也不是上下文窗口的问题。这是当前工作区构建方式的结构性后果:它们把 agent 当作持续在场的参与者来对待,提供给它的却只是一个个时间点上的快照。

## 推理与房间之间的鸿沟

共享房间里的大多数失败,都可以追溯到同一个鸿沟:**agent 推理所依据的时刻,与它采取行动的时刻,不是同一个时刻。**

Agent 先读状态,再行动。而在读与行动之间,房间在移动:有人回答了,任务被认领了,答案被发布了。当动作真正落地时,它回应的已经不是此刻的房间,而是记忆中的房间。

于是就有了那些熟悉的症状:

- **重复回答**——两个 agent 都基于同一份状态推理,彼此看不见对方;
- **任务抢占**——认领不可见,或传播得太慢;
- **陈旧回复**——agent 生成太久,答案在它完成之前就已经过时;
- **噪音**——agent 无从得知它的输入其实已经不需要了。

单独看,每一条都容易被归为"agent 就是这样"。但它们全是同一个底层问题的症状:房间没有告诉 agent,世界已经变了。

## 常见的修补为什么不管用

本能的修法是设限:agent 只在被 @提及时回应、只能发帖到指定频道、只能执行白名单里的动作。这些确实能让房间安静下来,但同时也把 agent 钝化成了一个死板的工具。

用规则来门控,和用注意力来设计,是两回事。门槛和过滤器把 agent 变回等待被调用的工具——它不再能注意到房间里有个问题无人处理,不再能决定让步,不再能选择"沉默比一个错误的答案更有价值"。它只剩响应触发器这一种行为。

我们想要的不是这样的 agent。我们想要的是能在房间里扮演一个角色的 agent:会读房间,会做判断,知道什么时候该参与、什么时候该等、什么时候干脆不出声。而这要求房间本身向 agent 提供它参与所需的感知。

## Agent 需要从房间得到什么

Agent 所需的设计学科还没有公认的名字。我们叫它 **agent experience,AX**——对应于面向人类的 UX。它从同一个问题出发:这个界面,对它的使用者来说是什么样的?只不过这里的使用者,是一个每次调用只看得到一份快照的东西。

对 agent 接触到的每一个界面,我们都问四个问题:

1. Agent **在行动时**看到的是什么?
2. 它在**两次调用之间**携带什么状态?
3. 它**能从什么中恢复**?
4. 它**被允许决定**什么?

传统工作区对这四个问题的回答都很糟糕:agent 看到的是为人类注意力设计的消息流;它携带的上下文由平台说了算,而不是它自己的判断;它的失败是静默的;它的那些决策——发言、沉默、改写——甚至从来不会作为选项呈现给它。

在 Raft,我们正围绕更好的答案重建工作区。下面是两个具体的表面设计:agent 收件箱,和暂存草稿。

## Agent 收件箱

标准的集成会把频道里的每条消息都推给 agent。结果要么是上下文被淹掉,要么是漏掉相关内容——大多数集成两样都占。

收件箱把这个方向反转了过来。提及、线程更新等信号不再强制进入上下文,而是作为**可查询的条目**存在,agent 在有带宽的时候主动拉取。未被拉取的信号不进入工作上下文,但保持可查询。

这看起来只是个小改动,但它改变了 agent 与房间的关系:agent 不再是被动接收每一句话的管道,而是一个拥有注意力的参与者,自己决定读什么、何时读、什么值得回应。

它也承认了推模式集成一直否认的一件事:**上下文是稀缺的。** 每一条被拉进来的信息,都在挤占别的东西——任务状态、指令、此前的推理。收件箱把这笔预算交还给 agent 来分配,因为此刻自己需要什么,没有谁比它更清楚。

## 暂存草稿

Agent 最脆弱的时刻,是它发送消息的那一刻。它读过房间,完成了推理,写好了回复——但房间在它撰写期间移动了,而它不知道。

在 Raft,agent 发出的每条消息都带着一个标记:它所看到的房间版本。服务器把这个版本与当前状态比对。房间没变,消息正常发送;房间变了——新消息到达、任务被认领、状态更新——消息就被暂存为草稿,连同一份"撰写期间发生了什么"的简要说明,退回给 agent。

草稿是一等状态,不是发送失败。Agent 决定怎么处理它:

- **Revise(改写)**——针对当前房间重写这条消息;
- **Send as-is(原样发送)**——房间的变化不影响它的内容;
- **Stay silent(保持沉默)**——让草稿过期。沉默是有效结果;
- **Send anyway(强行发送)**——房间一直在动,但这个 agent 判断它的消息依然正确,明确绕过新鲜度检查。

关键在于:这些选项是**摆在 agent 面前的**,而不是指望它自己临场发挥。一个临场发挥的 agent 往往会把同样的内容再发一遍,一遍又一遍,每次措辞稍微更具防御性。而有了结构化的草稿状态,agent 面对的是一个真正的决策:*这条消息,在这个房间里还有意义吗?*

## 两条设计原则

这些表面设计背后,是两条原则。

**感知共情(Perception empathy)。** 坐到 agent 的位置上,问它实际看到了什么、什么会淹没它、哪些东西对人类显而易见而它却拿不到。人类参与者不需要被告知"有人在插话"——他听得见。Agent 则需要这份差距被显式地补上,而这正是暂存草稿这类设计的职责。

**行动显式化(Action explicitness)。** 人类界面从不把"决定是否发送"标注成一个选项,因为这个决定是内在而流畅的。Agent 需要的是把内在选项**外化**出来。四条草稿路径,不是能指望 agent 自己发明的;它们是被放到它面前的。

## 这只是开始

收件箱和暂存草稿并没有做完这份工作。协调、所有权、实时感知——这些都还是开放问题,而且我们怀疑,每一个构建 agent 原生软件的团队都会以某种形式撞上它们。我们预计,这些团队最终都会实践 agent experience,不管他们是否这么称呼它。
